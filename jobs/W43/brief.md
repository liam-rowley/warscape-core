## Goal
`docs/DECISIONS.md`, `docs/BACKLOG.md` and `docs/BACKLOG_HARNESS.md` are tables every parallel branch appends to, with a next number each branch picks for itself. Measured 2026-11-05: renumbering and re-merging them cost about 2 h of sessions across napoleon J80 and core W34, W39, W40 and W31, and three plan pull requests that each passed alone took `docs/BACKLOG.md` over the doc cap and turned `main` red (issues #122, #123; #124 split the file). This job gives both tables the shape `registries/jobs/` already has, one file per row, with ids two branches cannot both take, so parallel branches stop colliding. The core migrates here; a consumer stays on its Markdown file until it opts in.

## Decisions already made (follow them; a deviation goes in the report with its reason)
1. **File layout: two dir-storage registries through the existing machinery.** `registries/decisions/<id>.json` and `registries/backlog/<id>.json`, schemas `schemas/decisions.schema.json` and `schemas/backlog.schema.json`, declared as `core:decisions` and `core:backlog`, in `[storage] dir`. Decisions fields: `id`, `date`, `who`, `decision`, `reversible` (a string, as the old rows carry text), `replaces` (optional array, `x-ref` decisions). Backlog fields: `id`, `change`, `why`, `raised`, `area` (`core` or `harness`, which replaces the two-file split). So `wsc reg`, `wsc find` and `reg check` work with no new storage code.
2. **The id rule: a non-sequential id, minted, never counted.** New ids are `<prefix><yymmdd>-<4 lower-case hex>`, for example `C261105-a3f2`, from `wsc reg add <registry> --mint key=value ...` (date from the clock, hex random, checked against the rows on disk). Why not an id allocated at merge: `main` takes no direct commits, so a merge-time number needs a bot commit after every squash, and the row a reviewer read would change after review. Why not a reserved ref (the `claims` model): it needs the network and a check that a row's number was really reserved. A random id needs neither, and two branches that still draw the same one meet as an add/add on one path, which git refuses rather than merges. **Existing ids stay valid:** `C1`-`C39` and every `B<n>` keep their numbers, and a schema pattern accepts both forms, so reports and reviews still resolve. Numbers are closed: a new numeric id is refused, so a removed backlog number can never be reissued.
3. **`[policy] decisions` carries over with one new value form.** `decisions = "registry:decisions"` names a registry; any other value stays a Markdown path and takes today's code unchanged (the default for every consumer). `repo.py` checks that the named registry is declared and in `[storage] dir`. New key `backlog = ""` (the core: `"registry:backlog"`) and `backlog_prefix = "B"`.
4. **Append only, as a file rule, on every branch kind, in `policy.py`:** under the decisions folder a path that exists on the base and is changed, deleted or renamed is refused with the Markdown rule's message (a reversal is a new row, with `replaces` naming the old one). So rows are immutable: stronger than a replacing row being allowed to edit, and the same as today. An added file must parse, its `id` must equal its file name and be the minted form with the prefix, `date` must be YYYY-MM-DD, `who` and `decision` non-empty, `reversible` `yes` or `no`, and each `replaces` a row at the head. Unparsable fails closed. **The "merge the base" error goes away:** `changed` is taken from the merge base, so a branch behind the base no longer touches another branch's rows. `added_decision_rows` keeps returning `{id, text}`, `text` being the `| id | date | who | decision | reversible |` line, so rule F and game modules read it unchanged.
5. **Backlog rows are not append only** ("remove a line when its change merges" stays): they may be edited and deleted. Only an added file's id is checked (the minted form), so a stale `B107` is refused.
6. **`plan_doc` stays a free-text key.** The core's value becomes prose naming the backlog registry and `wsc find`. The default is unchanged.
7. **`doc_size` needs no code:** row files are JSON, not living docs, and views are not committed, so no plan branch can take a table over the cap. Add a host test that shows it.
8. **Views (J55, C19): rendered, not committed.** `python3 wsc.py reg render` writes `_scratch/registries/decisions.md` and `backlog.md`. Decisions sort by date then natural id, backlog by natural id; add a natural sort in `render` rather than a second code path. Nothing in the backlog view claims a value order: a rank field would collide across branches exactly as a number does.
9. **The importer extends `reg migrate`:** `wsc reg migrate <registry> --from-md FILE [--set key=value] [--check]`, columns from the schema's `x-view`. `--check` compares every table row of FILE with the row files by field value and exits 1 naming each row that differs or is missing. B19 and B98 are handled, not hand-edited after the fact: split from the outer cells and state how in the report.
10. **`docs/DECISIONS.md` cannot be deleted on this branch, and that is the shape of the migration, for the core and for a game.** The job is judged with the base's rules (C24), and on the base `decisions_problems` refuses a head without the rows. So a migration is two pull requests: (a) this job adds the rows, flips the config and leaves every row line of the Markdown file byte-identical (its prose header may change: only row lines are compared, so it says the file is frozen and points at the registry); (b) after merge, a `meta/` branch deletes the file and the key below. `docs/BACKLOG.md` and `docs/BACKLOG_HARNESS.md` have no such rule and are deleted here.
11. **The window between (a) and (b) is guarded by code.** New key `[policy] decisions_retired = ""` (the core: `"docs/DECISIONS.md"`): while that file exists, the `registries` gate runs the `--check` comparison, so a stale branch that adds a Markdown row fails instead of its row vanishing. `gate_doc_paths` skips the retired file; `skips` finds a decision id through the row files in registry mode.
12. **This job's own decision is a minted row file** naming W43 (rule F's wording), not a `C40` line: the Markdown table is frozen from this branch on.

## Steps
1. `git fetch`; `python3 wsc.py gates --fast` for a baseline. Read "What exists". List the unmerged branches that change the three files (`git branch -r`, `git diff --stat origin/main...<branch>`) for the report.
2. **Failing tests first**, committed red: a change, a delete and a rename of a decision row file refused; an added row with a numeric id, a wrong file name, a bad date or bad JSON refused; a good minted row ok; a branch behind the base ok; `added_decision_rows` text and rule F in registry mode; a **head** that sets `decisions = ""` still judged with the base's value (C24); backlog edit and delete ok, a numeric add refused; two minted ids differ; `--from-md` round trip including a row with a pipe; `--check` exit 1 on a lost row; the retired-file gate; natural sort; `[gates] skip` by a row file; a Markdown repo (the fixture game) unchanged.
3. Build in order, one commit each, tests green at each: schemas and declarations; natural sort and `--mint`; `--from-md` and `--check`; the policy rules; the gate and `skips`.
4. **Migrate:** run the importer for the three files; `--check` all three and paste the counts (39, 49, 15); flip `wsc.toml`; delete the two backlog files; rewrite the `docs/DECISIONS.md` header; write this job's decision row. Then merge `origin/main` and run `--check` again, so a row merged meanwhile is not lost.
5. Docs: `CLAUDE.md` step 1 and `README.md` say how to read the decisions and the backlog (`wsc reg render`, `wsc find`) and how to add a row (`wsc reg add ... --mint`); `REVIEW.md` "Later" items; `CONSUMING_OPTIONS.md` the keys and the opt-in as two pull requests; `UPGRADING.md` the note for a pin bump.
6. `python3 wsc.py gates` (full), then from the branch checkout `python3 wsc.py policy --branch job/W43 --base origin/main` (read the output; never chain after a pipe).
